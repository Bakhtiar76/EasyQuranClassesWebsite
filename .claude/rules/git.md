# Git and GitHub Rules

Use Git as a clean checkpoint system for project code/configuration.

## Before a commit

- inspect `git status`;
- run/review `git diff --check`;
- review the relevant diff;
- run applicable verification;
- confirm no secrets, DB dumps, backups, caches, logs, or unrelated files are included;
- stage only intended files and review the staged diff.

Prefer explicit `git add <paths>` over blind `git add .`.

## Commit messages

Commit messages must be clean, clear, concise, brief, human-readable, and specific.

Preferred examples:

- `feat: add responsive course cards`
- `fix: correct mobile header spacing`
- `chore: add project safety rules`
- `docs: update deployment workflow`
- `refactor: reuse shared button styles`

Prefer one line and keep the subject around 72 characters or less.

Do not use vague or long AI-style commit messages. Do not add `Generated by Claude`, `Generated with AI`, `Co-Authored-By: Claude`, or other AI attribution. Do not mention Claude/AI in normal implementation commit messages.

## Commit boundaries

Commit coherent milestones, fixes, refactors, setup changes, or related documentation. Do not mix unrelated work and do not create a commit after every trivial edit.

## Branches and GitHub

Inspect existing repository rules first. If none exist, keep `main` production-ready and use concise `feature/`, `fix/`, or `chore/` branches when appropriate.

Do not push unless the user/task explicitly authorizes it. Never force-push, rewrite shared history, merge PRs, alter branch protection, delete remote branches, or change GitHub repository settings without explicit approval.

A GitHub plugin/MCP is not required for normal local commits. Use it only when GitHub PR/issue/repository operations materially benefit the workflow and access scope is appropriate.
